- (capability) CAP-1: discover strictly newer eligible releases from the installed channel at the existing GitHub destination; success excludes drafts, other channels, equal/lower versions, malformed versions, and incompatible payloads.
- (capability) CAP-2: check automatically at randomized times about three times per day; success demonstrates approximately three attempts per continuously running day, persistence across restarts, and no catch-up storm after sleep/offline.
- (capability) CAP-3: expose update availability and user-controlled download/install in the app; success shows version/channel, checking/up-to-date/error states, progress, retry, and later/restart actions without manual DMG replacement.
- (capability) CAP-4: complete a verified update without losing meeting work or local data; success relaunches into the chosen version and preserves settings, recordings, transcripts, notes, summaries, and model caches, while failures leave the current installation usable.
- (constraint) Keep the existing GitHub Releases destination, strict beta/stable isolation, semantic version ordering, and macOS arm64 support. Retain signing/notarization, sandbox/IPC/path restrictions, beta-first integration, personal-data guard, and explicit release authorization from AGENTS.md. Do not include protected branding or real personal data in new artifacts.
- (assumption) A1: Interpret about three per day as an average for a running app: independently random 6-10 hour delays, mean 8 hours. Persist a next-due timestamp; first launch schedules a delay; overdue launch/resume makes at most one attempt after 0-5 minutes jitter, then schedules normally. No checks while fully quit, no wake agent, no replay of missed intervals; manual checks do not postpone the existing schedule and concurrent checks coalesce. Respect server rate-limit retry times without tight automatic retries.
- (assumption) A2: Notify without interrupting; user explicitly starts the download and chooses installation/restart. Include manual Check for updates in Settings alongside the installed version/channel. No automatic download, forced restart, silent install on normal quit, or channel switch.
- (assumption) A3: Scope to the shipped signed macOS arm64 desktop app. Exclude extension self-update, Windows/Linux, rollback UI, delta-update optimization, telemetry, and staged rollout.
- (assumption) A4: Require active recording, Live transcription, processing jobs, and unsaved edits to finish/save before installation. Block the install action while unsafe and recheck in main at installation time; a timeout or failed save is not permission to replace the app. Persist downloaded readiness where supported; never auto-install merely because work becomes idle.
- (decision) Use brownfield.md for current code/release evidence and implementation constraints; use acceptance.md for channel, scheduler, installation, error, and release validation scenarios; adopt ../../../AGENTS.md as project policy.
- (decision) Implementation must add update-capable release payloads and channel metadata while preserving existing DMG links and release authorization. electron-updater is a candidate, not a fixed dependency: official electron-builder v26 auto-update documentation requires a macOS ZIP and metadata, and channel documentation warns GitHub channel detection differs; verify strict filtering rather than trusting allowPrerelease alone. Sources: https://www.electron.build/v26/docs/features/auto-update/ and https://www.electron.build/v26/docs/tutorials/release-using-channels/ .
- (decision) Validate release tag, metadata version, architecture, release prerelease flag and beta identifier together; reject inconsistent candidates, compare semantic versions rather than dates or strings, and select the greatest eligible version even if another channel appears first. Bind installation to the verified candidate; missing metadata is unavailable, not up-to-date. Do not silently fall back to another channel.
- (constraint) Update downloads must verify expected integrity and publisher signature, originate from the configured release source and valid asset redirects, and never accept arbitrary renderer-provided URLs/paths. Keep renderer APIs narrow and no bundled GitHub token. Recovery must report actionable errors, keep the installed app usable, and preserve cached models/user data.
- (note) Bootstrap limitation: installed builds without an updater need one manual installation of the first updater-enabled build. Adding assets to an old release cannot retrofit its installed binary. End-to-end updater validation requires two authorized signed versions per channel; this spec does not authorize building or publishing them.
- (question) Q1 implementation gate: select and verify the exact updater/provider integration, generated channel manifest names, signature/integrity checks, and macOS quit/install semantics against pinned dependencies. Prove beta-only discovery and deferred installation using real signed builds; do not infer these guarantees from a library flag.

These are implementation verification requirements, not claims of completed tests.
